# Smoke, fire, explosions and aircraft trails for Stratos

Research accessed **October 5, 2026**. Technical evidence comes from engine documentation, original research, original developer repositories and authoring-tool vendors. Proposed budgets and implementation order below are engineering recommendations, not measured Stratos performance or published market benchmarks.

## Recommendation and current fit

Stratos should begin with a **pooled, instanced billboard system using authored flipbooks**, plus a separate ribbon system for long aircraft and missile trails. Use alpha blending for smoke, additive emission for hot flame cores and sparks, depth fading at terrain intersections, and effect quality controlled by screen coverage. This offers the most useful visual improvement per implementation hour for the existing Three.js/WebGL game. Reserve volumetric ray marching and WebGPU compute for a measured second stage.

The inspected project uses Three.js `^0.186.1`, `WebGLRenderer`, ACES filmic tone mapping and a floating origin. Its exhaust is currently one mesh attached to the aircraft, scaled with throttle. There is no existing smoke, explosion or missile-trail pipeline. The first integration task is therefore a reusable effects manager; replacing the renderer first would add unnecessary dependencies to this work. Rapier should supply collision/damage events and moving debris bodies; thousands of visual smoke particles should not become rigid bodies.

The official Three.js fire/smoke example demonstrates instanced sprite materials, life-based opacity/scale and additive fire with depth writes disabled. It is a useful reference implementation, but its demo counts are not a performance guarantee for a terrain-heavy combat scene. [Official fire and smoke source](https://github.com/mrdoob/three.js/blob/dev/examples/webgpu_particles.html).

## What produces a convincing effect

Build explosions as a short sequence of distinct layers: a brief hot flash, expanding fireball, turbulent dark smoke, sparks/debris, a ground dust skirt where appropriate, and a longer residual plume. Each layer should have independent timing and bounds. An explosion that only enlarges an orange sprite reads as an icon; motion, evolving silhouettes and the transition from emission to opacity make it read as a physical event.

Use authored flipbooks to supply internal turbulence and density variation. Sample two adjacent atlas frames and interpolate rather than stepping visibly. Derive playback from particle age, with randomized starting phases for looping smoke and controlled phase for one-shot explosions. Bake padding around each atlas cell, dilate RGB into transparent edges, and inspect mip levels to prevent neighbor-frame bleed. These are pipeline recommendations for Stratos.

For smoke that must react to changing sunlight, author density/opacity and relighting information separately instead of baking a strong directional light into the color atlas. SideFX's Flipbook Textures tool explicitly supports multiple passes for relighting, frame interpolation and depth blending. Start with a simple sun/ambient approximation, then evaluate normal or directional-light-response textures when the base silhouette is convincing. [SideFX Labs Flipbook Textures](https://www.sidefx.com/docs/houdini/nodes/out/labs--flipbook_textures-1.0.html).

For the player jet, keep the hot exhaust core in aircraft space, near the nozzle. Emit smoke, contrails and wake remnants into world space so they remain behind during turns. Use a narrow emissive mesh or several anisotropic billboards for the flame, and add restrained bloom. Heat distortion is a separate scene-color sampling pass; add it only after verifying that distortion is depth-occluded and does not reveal silhouettes through the fuselage. Contrails should respond to the game's chosen altitude/weather rules; dense black smoke should convey aircraft damage, not ordinary flight.

## Particle pipeline and library choice

Allocate particle data once: position, velocity, birth time, lifetime, seed, size and atlas phase. Use typed-array pools and free lists, with a defined behavior when full: reject low-priority emissions or recycle the oldest low-priority particles. Update survivors without allocating vectors or constructing meshes every frame. Batch by material/atlas and use camera-facing quads through instanced attributes. Correct bounds must include the full evolving plume, not merely the emitter, or frustum culling can make smoke vanish while it is still visible.

Billboard quads allow rotation, anisotropic scale and large apparent particles without dependence on device point-size limits. Ribbons suit persistent trails: store a bounded ring buffer of sampled path points, build camera-facing segments, and widen/fade with age. A missile trail should not need hundreds of huge overlapping circular puffs merely to form a continuous line.

**Build-versus-adopt:** evaluate `three.quarks` in a small benchmark before writing a complete editor. Its repository provides a TypeScript effects system and batched rendering under MIT; it also lists WebGPU support as a roadmap item, so do not assume its current WebGL effects automatically become a production WebGPU solution. Maintain a thin adapter around whichever system is chosen. Library licensing does not grant rights to unrelated marketplace textures or example assets. [three.quarks repository and license](https://github.com/Alchemist0823/three.quarks).

Anime.js remains suitable for UI transitions and scripted cinematic parameters. Particle age, emission and trail sampling should follow the game clock so pause, slow motion, replay and fixed-step simulation remain coherent.

## Blending, transparency and depth correctness

Smoke attenuates the background and therefore needs ordinary or premultiplied alpha composition. Pure additive black smoke contributes nothing; additive gray smoke looks like illuminated fog. Fire's hot core and sparks can be additive, while its soot remains an alpha layer. Process the scene in linear color, then tone-map the final composition consistently. Keep the atlas encoding, shader output and blend factors in agreement; mixing straight and premultiplied alpha produces fringes.

For blended particles, the normal starting state is `transparent: true`, `depthTest: true`, `depthWrite: false`. Turning off depth testing makes smoke show through mountains; enabling depth writes causes translucent cards to reject later cards. A double-sided transparent material may introduce extra draws; use single-sided camera-facing geometry where possible or verify the material's single-pass option. [Three.js Material documentation](https://threejs.org/docs/pages/Material.html).

Three.js sorts transparent **objects**, not every triangle or instance inside a particle batch. Sorting a few emitter objects is consequently insufficient when plumes intersect. A baseline implementation can sort active smoke instance records back-to-front, or use approximate depth buckets and smaller spatial batches. Additive sparks are less sensitive to ordering. Alpha testing is appropriate for sharp cutouts, but is a poor main substitute for soft smoke opacity. [Three.js transparency manual](https://threejs.org/manual/pages/transparency.html).

Weighted blended order-independent transparency is an optional compromise for overlapping plumes: accumulation and revealage buffers avoid strict primitive sorting but approximate transmission. It requires extra render targets, blending support checks and a composition pass, and can misrepresent dense/high-opacity layers. Compare it against sorted alpha under realistic viewing angles before adoption. The original paper establishes the technique; it does not establish browser-specific speedups. [McGuire and Bavoil, Weighted Blended OIT](https://www.jcgt.org/published/0002/02/09/).

Soft particles fade opacity where a particle intersects opaque geometry. Render opaque scene depth to a sampleable texture, reconstruct **both depths into the same positive view-distance convention**, and use a fade such as `clamp((sceneDistance - particleDistance) / fadeMeters, 0, 1)`. Include a near-camera fade to avoid seeing a giant card plane. DepthTexture provides the relevant Three.js primitive. [DepthTexture](https://threejs.org/docs/pages/DepthTexture.html).

The old NVIDIA soft-particle sample documents the technique, but copying its comparison/sign literally into modern Three.js is unsafe. Perspective depth is nonlinear; reversed or logarithmic depth needs matching reconstruction, and WebGL and WebGPU clip-space conventions differ. Verify foreground aircraft, terrain contacts, camera-near particles and far-horizon precision with the exact renderer settings. [NVIDIA soft particles](https://developer.download.nvidia.com/SDK/10/direct3d/Source/SoftParticles/doc/SoftParticles_hi.pdf), [current WebGLRenderer depth options](https://threejs.org/docs/pages/WebGLRenderer.html).

## Motion, distance emission and floating origin

Emission per second alone produces stretched gaps when a jet accelerates. For trails, accumulate distance traveled and spawn at interpolated positions along the swept segment; retain a time-based minimum for almost stationary damage smoke. Cap catch-up emissions after a hitch or teleport. For fire sources, time emission is normally sufficient. Seed randomness for predictable debugging and consistent replay.

Drive old smoke through a shared world wind field plus buoyancy, expanding size and fading density. Use large-scale advection for the plume and smaller turbulence for its edges. Curl noise offers a divergence-free procedural velocity field, avoiding the artificial sinks that independent random velocity components can create. It approximates fluid-like motion without requiring a full fluid solver. [Bridson, Hourihan and Nordenstam, Curl-Noise for Procedural Fluid Flow](https://www.cs.ubc.ca/~rbridson/docs/bridson-siggraph2007-curlnoise.pdf).

For Stratos, retain authoritative trail anchors in world coordinates on the CPU and convert to render-local coordinates using `World.origin`; alternatively rebase every live particle and every trail point by the origin delta in one operation. Never rebase only the emitter. Wind/noise sampling must use a stable world-space coordinate or seed so the plume does not jump when the origin changes. GPU state should use local/chunk-relative coordinates with explicit rebase offsets to avoid large-coordinate float precision loss.

## Performance: prioritize pixels over particle counts

Smoke performance is frequently limited by transparent overdraw: twenty full-screen cards can be more expensive than many small distant particles. Start with emission caps, screen-size LOD, lifetime limits, atlas batching and emitter culling. Reduce particle density as the camera approaches a plume, where projected coverage becomes enormous. Prioritize player feedback, visible threats and nearby impacts over distant decorative smoke.

For large clustered battles, render soft smoke to a half-width, half-height target, then composite using scene depth. That quarter-pixel-count target reduces shading demand, but thin terrain silhouettes and foreground aircraft can create halos. Depth-aware upsampling and careful depth reduction are essential. Keep crisp sparks/debris and narrow trails at full resolution. NVIDIA's foundational chapter explains both the fill-rate savings and the unavoidable depth-downsampling tradeoffs; its historical FPS measurements are not transferable to Stratos hardware. [GPU Gems 3, High-Speed Off-Screen Particles](https://developer.nvidia.com/gpugems/gpugems3/part-iv-image-effects/chapter-23-high-speed-screen-particles).

Avoid one dynamic light and shadow map per flame. Use a bounded pool of unshadowed short-lived impact lights, with terrain emissive/decal cues where suitable. Full fluid simulation is a separate expensive approach requiring volume state, simulation passes and volume rendering; it is a useful high-end reference, not the browser baseline. [GPU Gems 3, Real-Time Simulation and Rendering of 3D Fluids](https://developer.nvidia.com/gpugems/gpugems3/part-v-physics-simulation/chapter-30-real-time-simulation-and-rendering-3d-fluids).

WebGL GPU simulation can use ping-pong position/velocity textures through `GPUComputationRenderer`; validate float render-target support and memory before selecting it. WebGPU can use storage buffers and compute for larger systems. Three.js's WebGPURenderer has a WebGL2 fallback, but this does not imply that every compute workload, custom GLSL material or postprocessing pass migrates without modification. CPU pooling remains useful for event-driven combat effects even with GPU rendering. [GPUComputationRenderer](https://threejs.org/docs/pages/GPUComputationRenderer.html), [WebGPURenderer](https://threejs.org/docs/pages/WebGPURenderer.html).

## Asset authoring and visual references

EmberGen is a relevant optional authoring package because its documented workflow exports flipbooks/image sequences; it need not run in the browser. Its current pricing page separates indie/hobby, studio, enterprise and educational eligibility and node-locked/floating arrangements. No purchase is necessary for this recommendation; verify the appropriate tier and asset redistribution rights before commissioning work. [EmberGen documentation](https://docs.jangafx.com/embergen/), [JangaFX current pricing and eligibility](https://jangafx.com/software/pricing).

Houdini Labs is useful for richer relightable exports. Houdini Indie is limited-commercial software, not an unrestricted free production license; SideFX's eligibility FAQ currently includes organizational revenue and funding conditions, and limits licenses. Use the official terms for the actual organization and delivery format rather than assuming hobby/student access covers commercial game assets. [SideFX Indie eligibility](https://www.sidefx.com/faq/question/who-may-use-indie/).

Study the publisher's **Ace Combat 7** trailer for the desired relationship between sky readability, aircraft silhouette, contrails and combat spectacle. Study Eagle Dynamics' official **DCS 2024 & Beyond** footage for a contrasting simulation presentation. These are art-direction references, not evidence of either game's proprietary rendering implementation; do not infer particle architecture from video. [Bandai Namco official trailer](https://www.youtube.com/watch?v=TwSASVf-0eY), [Eagle Dynamics official footage page](https://www.digitalcombatsimulator.com/en/news/newsletters/3835d6a01ff60597c1a3c993ff9c606a/).

## Recommended delivery tiers and acceptance checks

| Tier              | Implement                                                                                                                              | Evidence required before promotion                                                                    |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Baseline          | Pooled WebGL instanced smoke/fire, one explosion atlas, world-space ribbons, fixed-clock age, distance emission, rebasing, effect caps | Stable aircraft turns and origin shifts; no depth-through-terrain artifacts; memory reaches a plateau |
| Visual polish     | Frame interpolation, soft particles, sun-reactive smoke, limited impact lights, restrained bloom, adjustable quality                   | No terrain intersection seams or atlas bleed; silhouettes remain readable at noon and sunset          |
| Battle scale      | Screen-coverage LOD, reduced-resolution smoke, emitter spatial batches; evaluate OIT only if sorting is visibly inadequate             | Dense battle and camera-inside-plume benchmarks improve GPU time without obvious halos                |
| Optional high end | TSL/compute migration, selective volumetric hero effects, depth-correct heat distortion                                                | Browser capability tests, fallback parity and measured gain over WebGL baseline                       |

Create repeatable scenarios: one jet maneuvering with contrails; twenty visible missile trails; several overlapping ground impacts; a smoking aircraft crossing the origin threshold; a camera flying through a plume; pause/resume; and a ten-minute effects stress run. Record CPU/GPU frame time, draw calls, active particles, projected smoke area and texture memory at fixed resolution. A proposed desktop starting allocation is 1–2 ms GPU and under 1 ms CPU for effects at 1080p, with explicit quality reduction when exceeded. These are goals to measure, not achieved numbers. Scale assets and counts only after the representative battle case meets the chosen device budget.
